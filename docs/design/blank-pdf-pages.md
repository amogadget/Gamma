# 空白 PDF 创建与任意位置插页设计

## 1. 本轮实现：两种独立的新建内容

Gamma 的「+」菜单提供两个入口：

- **New note page**：普通 Gamma 笔记页面，没有 PDF 源，适合 Markdown/大纲。
- **New blank PDF**：独立 PDF notebook，有真正的 PDF 文件、`doc_id` 和同一个 Gamma page/block 身份，适合 Pencil 手写与录音。

空白 PDF 可选标题、A4/US Letter、纵向/横向和 1–100 个初始空白页，并继承当前文件夹。创建后直接打开，随后可进入 iPad **Pencil & Audio**。它不替换用户当前打开的文档，也不自动把文字 note 转成 PDF。

此功能是 Web 创建入口，因此部署后 Web/Desktop 的对应前端和 iPad 内的 Full Gamma 工作区共享。已发布的独立 Desktop 安装包需要包含这一更新后才会出现新入口；本轮不自动发布新安装包。

## 2. 创建协议与数据保护

`PUT /api/blank-pdfs/{canonical UUID}`：

```json
{
  "title": "Physics scratchpad",
  "page_size": "a4",
  "orientation": "portrait",
  "page_count": 3,
  "folder": "Classes/Physics"
}
```

- 需要真实账号 session，遵守现有上传/存储配额。
- 返回普通 Gamma root page block，properties 含 `doc_id`、`source_url`、`pdf_kind: "blank"` 和初始纸张参数。
- PDF 用现有 PDF writer 生成，无外部下载、无 AI 调用。
- PDF 内加入本次创建身份，使两本同尺寸的空白 notebook 不因初始内容相同而合并成同一个 `doc_id`。
- PDF 源仍按既有 digest 命名、作为不可变文件保存。标题后续修改不重写 PDF。
- 客户端为一次创建保留同一 UUID 和 payload；响应丢失后 Retry 不另建一份。
- 服务端保存创建 payload 的指纹。同 ID/同创建请求返回当前 block，不覆盖后来重命名或移动文件夹的结果；同 ID/不同请求返回冲突。
- 文件原子发布与数据库写入配合；已知失败清理本次新文件。崩溃留下的文件不能与另一文档混用，同 ID 重试可恢复创建流程。
- `pdf_kind: "blank"` 用于避免自动进行 arXiv/DOI/AI 文献元数据识别，不是任意改写文件的授权标记。

## 3. 能否插入空白页？

**可以。** 但“生成白页”很简单，“在已有内容中安全插页”不是单纯调用 PDF writer 就结束。

当前客户端把下面的数据绑定到物理页码：

- 手写 block 的 `pdf_page`；
- 高亮的 `pdf_position.pageNumber`、boundingRect/rects 中的页号；
- 录音 `replay_events.pdf_page`；
- PDF 链接、引用跳转、查找结果、页图缓存与阅读位置；
- 原生缓存与待同步 mutation 中的文档 ID/页码。

例如，在第 2 页后插一页，原第 3 页变成第 4 页。如果只改 PDF 而不调整这些关联，手写可能显示到白页上，录音回放也会跳错页。

更重要的是，现有原生缓存按 `pageID/docID` 校验身份并保持源不可变；原地覆盖同一个 `<doc_id>.pdf` 会让不同设备拿着不同内容却以为它们是同一源。这个设计不能为了插页而绕过。

**本轮仅交付创建，不开放未经迁移验证的“原地插页”按钮。**

## 4. 推荐的插页模型

### 4.1 保持知识页身份，版本化 PDF 源

建议保留 Gamma page block ID（页面链接和 note tree 不变），引入明确的 document revision：

```text
Gamma page（稳定 ID）
  ├─ revision 1 → 原始不可变 PDF asset
  ├─ revision 2 → 插页后的新 PDF asset
  └─ current revision + page identity/order mapping
```

插页生成新 PDF 源及新 `doc_id`/source URL，不覆盖旧文件。旧版本保留用于回滚和明确的历史访问。旧 doc_id 的 by-doc 解析也要定义版本归属，不能悄悄创建第二个无关联知识页面。

### 4.2 页身份与页序分离

更长期的模型使用稳定 `pdf_page_id`，页面顺序独立维护：

```text
原顺序：[A, B, C]
在 B 后插页：[A, B, N, C]
C 的身份不变；物理序号从 3 变为 4。
```

批注/Replay 最终应引用稳定页身份，物理页码仅为显示/兼容索引。对于已有按数字页码存储的数据，需要一次显式映射迁移，不能假设已经拥有稳定页 ID。

不建议把这个字段先填上就宣称解决了插页：所有读写路径、旧客户端和缓存都必须理解这个映射。

### 4.3 一次插页操作的事务边界

建议专用接口提交：目标 Gamma page、预期 document revision/source hash、插入位置、数量、纸张尺寸。流程：

1. 明确插入在第几页之前/之后，校验权限、版本和资源限制。
2. 生成新 PDF 文件和旧页到新页的映射，保留旧文件。
3. 在服务器事务中更新当前 revision、source URL、页序、批注索引和相关录音事件。
4. 完成后重建/失效全文、页图、引用定位等派生缓存。
5. Web 重新加载新 source；原生执行显式缓存/队列迁移。
6. 失败不发布半更新的文档与页码组合，允许回滚。

当旧页的几何和旋转不变时，PKDrawing 的页内坐标以及 stroke PNG 通常不必重画；需要迁移的是页身份/页序关联。但复制页、裁切、缩放或旋转源属于额外几何操作，不能使用同一假设。

## 5. 离线客户端与 Replay 是主要风险

### 5.1 不能只检查服务器上有没有批注

即使服务器看起来没有批注，另一台离线 iPad 也可能有未上传的旧页码 mutation。因此“只允许未批注文档插页”并不能完全保证安全。

修改过页序的文档应要求客户端提交预期 document revision/source identity。旧客户端缺少版本信息时，应明确要求升级/迁移，不能把文档版本冲突当普通 ink revision 冲突，更不能让“使用本地版本”把笔迹写到错误页上。

### 5.2 原生缓存与 outbox

当前缓存身份检查失败时保留数据并报错，这是保护，不应简单删掉旧缓存重新下载。插页需要：

- 保留旧 revision 的 PDF 和页快照；
- 用已知 page mapping 对 pending 操作重新定位；
- 无法安全 rebase 时保留待处理分支，给出明确恢复流程；
- 只在迁移成功后切换当前版本。

### 5.3 Replay 的语义选择

推荐 Phase5A 继续跟随“当前最终笔迹/页布局”，通过稳定页 ID 或映射找到原来录制的内容。后来插入的空白页没有录音事件，不应凭空出现时间戳。

若希望回放时严格显示“录制当年的 PDF 版本”，应把录音绑定特定 document revision，提供历史视图。这是另一种产品语义，需要显式设计，不能与当前最终状态回放混用。

## 6. 普通 note 怎么办？

如果“已有 note”指带 PDF 的 Gamma 页面，可以按上述版本/映射模型考虑任意位置插页。

如果指纯 Markdown/大纲 note，它本身没有物理 PDF 页。可考虑两个不同功能：

1. **为此 note 附加空白 PDF**：保留原 Gamma page ID 与 children，新增独立 PDF 源，让该页面成为可手写的 notebook；不自动把现有文字排版进 PDF。
2. **在正文某处嵌入手写页/画布 block**：这是混合内容编辑能力，不等于修改一份 PDF 的页序，需要单独定义布局和导出。

不应为了支持“插空白页”而强制把所有普通 note 转为 PDF，丢掉 Markdown 编辑、引用或树结构。

## 7. 建议的实施次序

1. **已实现**：新建独立空白 PDF，可预先选择多页。
2. **下一步建议**：先为新空白 notebook 做版本化源和缓存更新，优先支持末尾追加——它不改变旧页序号，迁移明显简单。任意位置插页再补完整页映射/稳定页身份及离线队列 rebase；不能把两者当成同样风险的小操作。
3. **再扩展到已有文献 PDF**：验证书签、内部链接、页标签、表单、加密/签名、混合尺寸和嵌入批注。插页后的文件不能声称仍保有旧文件的数字签名有效性。
4. **普通 note 附加 PDF/嵌入手写页**：作为明确且独立的用户操作。

过渡期还可提供“另存为插入空白页的新副本”，保留原文档完全不动；但若同时复制 annotations/audio，需要重映射 block 引用和 Replay 关联，不应默默丢掉原有笔记。

## 8. 验收重点

创建：两种入口明确、独立身份、实际空白页/尺寸、当前文件夹、错误重试不重复、配额失败无残留、账号隔离、标准 PDF 兼容性。

本轮验证：后端全套 500 项通过（其中空白 PDF 专项 11 项），Web 单元测试/ESLint/build 通过；Chromium 验证了两个创建入口、纸张选项、模拟丢响应后的同 ID Retry，以及 pdf.js 打开三页空白 PDF。部署后也对实际前端 bundle 重跑了流程测试，API 使用隔离合成响应，没有向真实用户库写入测试文档。线上健康和新增 OpenAPI 路径已检查；部署前保留了一致数据备份。

插页未来验收：原件可恢复；所有旧内容仍对应正确页；crop/rotation 坐标不变；录音回放匹配原内容；离线旧客户端不会错写；中途失败无半迁移；版本间链接/搜索/缓存行为明确。
