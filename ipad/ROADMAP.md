# Follow-up roadmap

This began as a post-icon-update plan. Native text selection/highlight creation, full Web workspace reuse and browser Replay have since been delivered. The authoritative current design and remaining work are in [the unified design](../docs/design/handwriting-recording-ipad.md) and `WEB_PARITY.md`. The original ordering below is retained as decision history, not an assertion that every item is still unimplemented.

## 1. Original Web/Desktop parity plan

Original priority order:

1. **PDF text selection and native highlight creation.** Introduce an explicit Reading/Selecting versus Pencil-editing mode so text selection does not compete with handwriting. Use PDFKit selections and preserve Gamma's existing `highlight_id`, quote, page and position properties; highlights and note blocks must remain the same objects as on Web/Desktop.
2. **Markdown rendering parity.** Headings, lists/tasks, quotes, links, images, code blocks, tables, inline/display math and Gamma block references/embeds should render consistently. Establish a shared corpus from existing Web tests before choosing an editor/renderer.
3. **Editing/tree parity.** Add formatting actions, keyboard shortcuts, indent/outdent, reordering and references while retaining local-first persistence and safe server updates.
4. **Library/navigation parity.** Expand ordinary notes, full search, labels/folders and cross-document links without presenting unavailable controls as implemented features.

### Reuse strategy

Gamma Desktop is an Electron application containing the React/pdf.js/CodeMirror web frontend; it is not an AppKit implementation that SwiftUI can directly reuse just because both run on Apple hardware. Reuse API contracts, schemas, interaction semantics, test fixtures and appropriate web editor/Markdown components. A narrowly scoped WKWebView for rich Markdown/math is worth evaluating; keep PDFKit/PencilKit native rather than replacing the whole reader with a web wrapper. Compare native and embedded editors for input latency, keyboard/IME behavior, accessibility, offline edits and focus handoff.

## 2. Browser Note Replay

Implemented Phase 5A: Web Note Replay now combines the audio timeline with native-exported per-stroke PNG/path data, progressive masks, cross-page seek and click-ink navigation. See `../docs/dev/note-replay.md` for usage, automatic old-ink backfill, tests and limits. Exact erase/undo history remains out of scope.

Original design considerations (retained for context):

- Reuse the audio block's validated `replay_events` and segment-derived time offsets.
- Drive a browser player from audio currentTime; support play/pause, seek, cross-page restoration and click-ink navigation.
- Preserve Phase5A final-surviving-stroke semantics; do not imply exact erase/undo history.
- **Resolve stroke rendering first:** the browser cannot decode PKDrawing and a single PNG preview cannot reveal strokes independently. Evaluate a content-addressed, read-only replay preview asset (per-stroke SVG paths or bounded raster layers) generated by iPad alongside the editable PKDrawing. Specify coordinate space, stroke IDs, color/opacity, clipping/masks and asset limits.
- Treat any new preview format as untrusted input: prefer bounded numeric path data; if SVG is used, prohibit executable/external content and apply safe serving/CSP rules. Do not weaken the existing private asset policy.
- Keep editable PKDrawing as the source of truth. A display-only Web representation must not become an incompatible second editable drawing database.
- Add deterministic multi-page/crop/rotation tests, timestamp/segment tests and real browser seek tests before enabling the player.

Simply renaming HTML audio controls to “Replay” would not deliver Notability-style playback; this work includes the missing per-stroke visual representation and synchronization engine.
